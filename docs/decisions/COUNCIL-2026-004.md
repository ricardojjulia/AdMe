# COUNCIL-2026-004: Privacy-Preserving General Location & Zero-Knowledge Proximity Architecture

**Status:** RATIFIED — Completed
**Date:** 2026-09-08
**Council:** Architecture Council, AdMe (6/6 ratified)
**Related:** COUNCIL-2026-001
**Tags:** council, automatic, live-governance, privacy, location

## Context
AdMe aims to show geographically relevant content (e.g. local merchant deals, regional preferences, community campaigns) without violating its core privacy-first ethos. Traditional platforms harvest precision GPS coordinates, construct historical location traces, and store them in centralized databases for ad targeting. We need an architectural pattern that allows general/coarse location detection (city/region) and proximity matching while maintaining user trust, transparency, and zero persistence of user location coordinates in any cloud database.

## Decision
Implement a hybrid privacy-first location architecture:
1. Passive Edge-Based Coarse Detection: Read standard edge CDN headers (e.g., 'x-vercel-ip-city', 'x-vercel-ip-country-region', or fallback) on incoming requests to establish a general city/metro baseline without browser permission prompts or fingerprinting.
2. Active Client-Side Quantization: If the user opts into localized proximity deals, browser geolocation coordinates are immediately quantized/fuzzed on-device to ~1-5km neighborhood grid cells (rounding to 2 decimal places max) and stored strictly in ephemeral client memory / local state.
3. Zero Cloud Persistence: User coordinates or location histories are NEVER persisted to the Supabase database (users table or logs). Content filtering against location happens either on-device or via ephemeral coarse bounding queries.
4. User Agency & Transparency: Provide an overt location badge (e.g., '📍 Santa Monica, CA · Evaluated on-device · Zero tracking') with controls to toggle off, blur, or manually override location at any time.

## Amendments Adopted
1. Strict Zero-Telemetry Rule: Lat/lng coordinates and raw IP addresses must be added to telemetry/logger redaction lists to prevent accidental ingestion in observability tools (Sentry, PostHog, Vercel Analytics).
2. Quantization Guard: Quantization must occur synchronously in the browser before any state dispatch, capping precision at 2 decimal places (~1.11km at the equator).
3. Database Schema Constraint: Absolute prohibition on adding user-specific location, GPS, or historical geofence columns to Supabase tables or session tokens.
4. Manual Override Fallback: Users must have an explicit UI mechanism to set a manual city/metro or completely disable location-aware deal sorting without degrading non-location features.

## Implementation Mandate
1. Create `src/types/location.ts` with strict TypeScript models (`CoarseLocation`, `QuantizedCoordinates`, `LocationSource`, `LocationState`).
2. Implement `src/lib/location/quantize.ts` providing pure functions `quantizeCoordinates(lat, lng, decimals = 2)` and Haversine distance calculator `calculateHaversineDistanceKm()`.
3. Implement `src/hooks/usePrivacyLocation.ts` managing edge headers hydration, browser geolocation opt-in with immediate quantization, and client-side manual overrides.
4. Build `src/components/location/LocationBadge.tsx` and `LocationSettingsModal.tsx` providing transparent user status, blur/fuzz toggles, and manual city picker.
5. Configure Next.js edge middleware (`middleware.ts`) to forward coarse geo headers (`x-adme-city`, `x-adme-region`, `x-adme-country`) safely.
6. Write unit tests in `src/lib/location/__tests__/quantize.test.ts` and integration tests asserting zero Supabase API coordinate leakage.

## Council Deliberations
### 🏛️ The Architect (YES)
The hybrid edge/client approach fits Next.js App Router architecture cleanly. In `middleware.ts` or Server Components, we can read Edge geo headers (`x-vercel-ip-city`, `x-vercel-ip-country-region`, `x-vercel-ip-latitude`, `x-vercel-ip-longitude`) provided by the hosting platform, or use `@vercel/functions/geolocation`. We can hydrate an initial read-only `CoarseLocation` state without triggering browser permission prompts. When deals or campaigns request proximity, the client executes distance filtering locally using Haversine calculation against coarse deal centroid coordinates fetched in broad metro batches. This completely avoids sending user coordinates to the database.

### ⚙️ The Engineer (YES)
Implementation will be clean and modular. We will introduce `src/types/location.ts` defining `CoarseLocation`, `QuantizedCoordinates`, and `LocationPrivacySettings`. A custom hook `usePrivacyLocation` will wrap `navigator.geolocation.getCurrentPosition` with an immediate transformation pipeline: raw `(lat, lon)` is passed to a pure function `quantizeCoordinates(lat, lon, precision = 2)` (yielding ~1.1km resolution) and raw values are garbage collected immediately. Location state will reside in an ephemeral Zustand or React Context store, defaulting to SessionStorage or memory only, with zero sync to Supabase user profiles.

### 🛡️ The Security Lead (YES)
This proposal provides an exemplary privacy-preserving paradigm that eliminates coordinate leak vectors. To guarantee zero-knowledge proximity, we must enforce three guardrails: 1) Geolocation coordinates must never be passed as URL query parameters or in Supabase RPC calls; 2) Error logging and telemetry (e.g., Sentry, PostHog) must explicitly sanitize/strip GPS fields; 3) Edge CDN headers used for coarse initial detection must be stripped of precise IP addresses prior to client-side logging. With these constraints, GDPR Article 5(1)(c) data minimization is strictly satisfied.

### 🎯 The Product Owner (YES)
This strongly reinforces AdMe's value proposition of radical privacy and user empowerment. The overt status badge ('📍 Santa Monica, CA · Evaluated on-device · Zero tracking') turns what is normally a suspicious tracking mechanism into an active trust builder. Users will have full control via a Location Privacy modal: they can toggle between 'Auto Coarse (Edge)', 'Neighborhood (Fuzzed On-Device)', 'Manual City Selection', or 'Disabled (Global)'. This transparency directly counters ad-tech surveillance fatigue.

### 🧪 The QA Lead (YES)
We can build deterministic, automated test suites around this design. Unit tests will validate `quantizeCoordinates` against boundary conditions (e.g., coordinate clipping at ±90/±180, rounding precision drift, null/invalid inputs). Integration tests will mock `navigator.geolocation` permission denials, edge header fallbacks, and local storage overrides. Network assertion tests will verify that zero outgoing Supabase REST/GraphQL/RPC payloads contain latitude or longitude fields during deal interaction flows.

### 💾 The Data Engineer (YES)
I endorse this zero-persistence invariant. In the Supabase PostgreSQL schema, the `merchants` and `campaigns` tables may store coarse bounding metadata (e.g. `target_metro: text`, `target_postal_prefix: text`, or a public merchant centroid `lat/lng`), but the `users`, `profiles`, `ad_impressions`, and `analytics_events` tables must contain NO coordinate or location history columns. Filtering queries will fetch active deals by broad metro/region slugs, allowing the client to execute local proximity scoring in-memory.
