# COUNCIL-2026-006: Contextual Media Deep Resolution, Anti-Repetition Photo Pools, and Bespoke Editorial Visual Generator

**Status:** RATIFIED — Unanimously Approved for Implementation
**Date:** 2026-09-14
**Council:** Architecture Council, AdMe (6/6 ratified)
**Related:** COUNCIL-2026-004, COUNCIL-2026-005
**Tags:** council, media, image-quality, visual-design, openstreetmap, wikimedia, editorial-generator

## Context
A visual inspection of the live consumer feed revealed several deficiencies in media representation:
1. **Generic & Repeated Stock Placeholders**: All venues within a category shared a single static image (e.g. every restaurant displayed the identical dining room photo, every coffee shop displayed the identical green lamp photo).
2. **Aggressive Vertical Cropping**: In `NativeAdCard`, landscape photos placed in a rigid 30% width container were magnified ~300% and vertically cropped, cutting off focal subjects and displaying awkward floorboards or ceilings.
3. **Mismatched Marketplace Imagery**: Certain syndicated classified listings displayed irrelevant photos (e.g., a solid walnut mid-century credenza displayed a modern coworking office lounge).
4. **Lack of Graceful Fallbacks**: Missing or broken image URLs left blank spaces or broken badges with zero aesthetic polish.

## Decision
Ratify a 3-tier visual quality and media enrichment architecture:
1. **Tier 1 — Deep Authentic Media Resolution**:
   - Query OpenStreetMap with `&extratags=1&addressdetails=1`.
   - When `wikidata`, `wikipedia`, or direct `image` tags are present, query Wikimedia Commons / Wikipedia PageImages API to retrieve authentic storefront and venue photographs.
2. **Tier 2 — Contextual Anti-Repetition Photography Pools**:
   - Construct comprehensive, curated multi-photo pools per category and cuisine/vibe.
   - Use deterministic string hashing (`hashString(name + address) % pool.length`) so adjacent venues in the feed never share the same image.
   - Expand the marketplace catalog to 10 authentic items with verified matching photography.
3. **Tier 3 — Bespoke Editorial Visual Generator (`EditorialVisual.tsx`)**:
   - When an authentic image is unavailable or an image fails to load (`onError`), render an editorial card banner featuring a multi-color mesh gradient, brand monogram crest, subtle vector pattern, category pill, and verified rating badge.
   - Refactor `NativeAdCard.module.css` to a balanced 38% width with centered object positioning to prevent awkward cropping.

## Council Deliberations

### 🏛️ The Architect (YES)
The 3-tier progressive resolution (Wikimedia deep lookup -> Deterministic diverse pools -> Client-side editorial visual generator) is resilient, performant, and ensures zero broken imagery with no external paid dependencies.

### ⚙️ The Engineer (YES)
The implementation is clean. Nominatim extra tags are already provided in the response payload. The deterministic hashing is computationally trivial (O(N) string hash) and eliminates feed visual monotony. The `EditorialVisual` component is pure React + SVG/CSS with zero runtime bloat.

### 🛡️ The Security Lead (YES)
Wikimedia Commons and Wikipedia APIs are open, public, and require no API secrets. SVG generation is performed client-side using parameterized JSX with sanitization, eliminating XSS vectors.

### 🎯 The Product Owner (YES)
This directly addresses user dissatisfaction with repetitive and ugly imagery. The feed will feel alive, authentic, and curated like a high-end editorial magazine.

### 🧪 The QA Lead (YES)
The deterministic hashing and fallback handling are easily unit-tested. We will verify that different place names produce distinct images and that image error events cleanly render the fallback artwork.

### 📊 The Data & ML Engineer (YES)
Varied visual stimuli significantly improve user dwell time and engagement, reducing ad fatigue and banner blindness.
